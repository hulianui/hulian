# 瑚琏双语文档站与组件快速直达设计

**日期：** 2026-08-01

**状态：** 已确认

**范围：** `apps/www` 的全部公开页面、预览与演示，以及它们读取的文档、元数据和展示数据

## 目标

1. 国内镜像 `hulianui-zh.haloritual.com` 与国外主站 `hulianui.haloritual.com` 都同时提供完整中文和英文模式。
2. 国外主站首次访问默认英文，国内镜像首次访问默认中文；用户手动选择后，两站各自记住选择。
3. 英文模式覆盖整站，不局限于顶栏：组件文档、主题、区块、页面、更新日志、搜索、全部演示、业务样例、错误与空状态、无障碍名称、页面元数据和代码示例中的展示文案都必须为英文。
4. 用户可从首页、全站搜索、组件目录、组件详情和文档内引用快速进入对应组件详情页，且跳转保持当前语言。
5. 保留现有中文 URL，避免破坏已发布链接；英文页面拥有稳定、可分享、可索引的独立 URL。

## 非目标

- 不改变 `@hulianui/ui` 的公开组件 API。
- 不为中英文维护两份可独立漂移的 React 页面树。
- 不把自动机器翻译服务放进生产运行时。
- 不将中国专用组件的真实数据标识伪造为另一套数据。品牌名“瑚琏”、法规名称、行政区划原名等必要专名可在明确标注的位置保留，并提供英文解释。

## 已有约束

- 文档站使用 Next.js App Router 和 `output: "export"`，所有动态路由通过 `generateStaticParams` 生成。
- 两个公开域名消费同一仓库的静态站产物，但部署链路不同。
- 中文路由已经公开，例如 `/components/button`，不能整体迁到 `/zh/components/button`。
- 当前存在 123 个 `page.tsx` 页面入口、372 份组件 Markdown；大量演示文案分布在页面组件与 `_data` 模块中。
- 工作树可能同时存在其他组件开发，双语改造必须保留并兼容这些变化。

## 方案取舍

### 采用：同源双静态构建

同一份源码按 `DOCS_LOCALE=zh-CN` 与 `DOCS_LOCALE=en` 顺序构建两次：

- 中文构建保持现有路径与资源路径。
- 英文构建设置 `basePath=/en`，生成同构的英文站。
- 构建脚本把中文产物作为根目录，把英文产物完整合并到根产物的 `en/` 子目录。
- 两个域名部署完全相同的合并产物，因此任意域名都能访问两种语言。

该方案保留现有中文 URL，同时让英文页面成为真实静态 HTML。页面正文、`html[lang]` 和 metadata 在构建期就已确定，不依赖水合后替换。

### 不采用：单页运行时词典切换

运行时切换只生成一种首屏 HTML，容易出现语言闪烁，英文 metadata 与搜索索引也不完整。它适合应用内小范围文案切换，不满足完整英文文档站的可索引要求。

### 不采用：两个域名单语构建

分别给两个域名只部署一种语言会让切换变成跨站跳转，也会产生构建配置和内容漂移；它不满足“两站都具备英文模式”。

## 国际化库选型

参考 FormatJS、react-i18next 与 react-intlayer 的能力后，采用 `react-intlayer` / `next-intlayer` 作为内容声明和 React 集成层：

- 它同时覆盖 Server Component、Client Component、类型化内容声明、就近词典和 Markdown 渲染，适合本项目大量页面与演示内容分散在各自目录的结构。
- `next-intlayer` 的自动语言中间件和 `[locale]` 路由不用于生产，因为静态导出没有请求期中间件，且本项目必须保留无语言前缀的现有中文 URL。
- Intlayer 只负责内容选择、格式化、Provider 与开发期完整性检查；`/en` 路由仍由双静态构建产生。
- 关闭 CMS live sync、远端词典和 AI 自动补译。所有发布内容必须进入 Git、可复核、可重复构建。
- 长篇组件 Markdown 继续保留独立源文件，由 Intlayer 的 Markdown 能力或现有 `Markdown` 组件渲染，不把数百篇正文硬塞进 JSON。

不选择 FormatJS 作为主层，是因为它擅长 ICU message、数字和日期格式化，却不解决本项目的静态双路由与内容共置；必要的复杂复数和格式化仍可使用原生 `Intl`。不选择 react-i18next 作为主层，是因为它的成熟运行时和命名空间能力足够，但本项目更需要编译期类型、页面就近内容和 Markdown 内容组织。若 Intlayer 在最小技术验证中无法与 Next 16、React 19、TypeScript 7 或 `output: "export"` 稳定共存，唯一允许的回退是 `i18next` + `react-i18next`，且必须保持本文定义的路由、无中文回退和验证契约不变。

## 路由与默认语言

中文和英文一一对应：

```text
/components/button       <-> /en/components/button
/demos/crm/customers     <-> /en/demos/crm/customers
/theme/color             <-> /en/theme/color
```

顶栏语言切换使用普通同域导航而不是客户端软路由，因为它跨越两次独立静态构建。切换时保留 pathname、query 和 hash，并先写入 `localStorage` 的显式语言偏好。

中文构建的根布局包含一段在页面绘制前执行的最小脚本：

- 已选择英文：任意域名访问中文路径时进入对应 `/en` 路径。
- 已选择中文：保持中文路径。
- 没有偏好：国外主站进入英文对应路径；国内镜像保持中文。
- 本地开发和未知预览域名默认中文，开发者可手动切换。

英文页面不再重复自动跳转。切回中文后记录偏好，避免国外主站再次把用户送回英文。

## 国际化边界

### 站点基础层

基于 Intlayer 建立类型安全的文档站国际化层，并补充项目专用 URL 辅助模块，提供：

- 当前构建语言常量。
- 顶栏、搜索、组件目录、预览工具、安装面板、复制反馈等共享词典。
- 页面就近的双语内容声明，以及仅在构建期确定结果的数据选择辅助函数。
- raw URL、资源 URL、canonical、alternate 和语言切换 URL 的统一生成函数。
- `ConfigProvider` 对接：中文构建使用 `zhCN`，英文构建使用 `enUS`。

缺少英文键必须在类型检查或构建时失败，不允许静默回退到中文。

### 结构化元数据

以下单一真源增加英文展示字段：

- 组件 `manifest`：分类、小类、短名、描述。
- 区块、页面与演示 meta：名称、描述、标签、分类。
- 主题导航与搜索指南。
- changelog 的英文标题和正文。

slug、组件导出名、安装依赖和 registry 标识不做语言分叉。

### Markdown 与组件说明

每份公开组件文档使用并列的英文 Markdown 源。加载器按构建语言选择文件；英文文件缺失时构建失败。英文 Markdown 保持与中文文档相同的章节、API、示例和相关组件链接。

生成 `llms.txt`、`llms-full.txt`、registry 文档数据时同时产生英文版本，并把英文站内链接指向 `/en/components/<slug>`。中文现有生成物保持兼容。

### 页面、演示和业务样例

页面内散落文案迁移为以下两类之一：

- 跨页面复用的界面词进入共享词典。
- 页面专属内容留在就近的双语数据对象中，避免形成一个无法维护的巨型词典。

演示数据的姓名、公司、订单、通知、客服对话、课程、商品、错误信息和空状态都提供英文版本。代码示例中的注释和用户可见字符串随语言切换；组件名、API 名、命令和真实协议字段保持原样。

带文字的静态图片需要替换为无文字素材或提供英文变体。品牌名、法规原名和中国行政区划等确需保留中文的节点必须显式标记 `data-i18n-allow-cjk`，同时展示英文解释，不能用大范围目录白名单绕过门禁。

## 组件快速直达

### 全站搜索

- 搜索索引同时包含组件英文名、中文短名、slug、导出别名、分类和用途关键词。
- 精确命中唯一组件时，回车直接进入组件详情。
- 多结果仍按页面、区块、组件、演示、指南分组展示；结果 URL 使用当前语言。
- 空查询时提供“快速找组件”组，展示最近新增与常用组件，而不是空面板。

### 首页与组件目录

- 首页“组件”档从只链接十个大类，升级为分类入口加可搜索的组件快速入口。
- 输入 `Button`、`按钮`、`button` 或已登记别名即可直接打开 `/components/button` 或英文对应页。
- 组件目录页顶部保留同一快速入口；左侧组件树继续提供完整分类浏览。
- 大量组件不一次性塞满首页；无搜索时展示常用和最近新增项，并提供“查看全部组件”。

### 组件详情与文档链接

- 左侧树、面包屑、相关组件和 Markdown 内组件引用全部生成真实详情链接并保持语言。
- 详情页底部提供上一组件、下一组件和返回当前分类。
- 文档加载器继续重写相对“相关组件”链接，并新增链接完整性检查，禁止指向不存在的 slug。
- 复制给 AI 的 Markdown 使用公开主站绝对 URL；英文页复制内容指向英文 URL。

## SEO 与可访问性

- 中文 HTML 使用 `lang="zh-CN"`，英文 HTML 使用 `lang="en"`。
- 每个公开页面生成语言对应的 title、description、Open Graph、结构化数据和面包屑。
- canonical 指向主站的当前语言 URL；`alternates.languages` 同时声明 `zh-CN`、`en` 与 `x-default`。
- 国内镜像继续 canonical 到国外主站，避免镜像内容重复收录。
- 语言切换具备明确的可访问名称与当前语言状态，在移动端和桌面端都可操作。
- 组件快速入口支持键盘输入、方向键、Enter 跳转、Esc 关闭和可见焦点。

## 失败处理

- 缺少英文词典键、英文 Markdown、英文 meta 字段或对应静态路由时，构建直接失败。
- 语言偏好存储不可用时仍可完成一次切换，只是不持久化。
- 自动默认语言脚本异常时保留当前中文页面，不制造跳转循环或空白页。
- 组件快速入口没有命中时提供全站搜索和组件目录出口。
- 双语合并脚本只操作仓库内明确的临时产物目录；任何一步失败都不覆盖上一次成功产物。

## 验证与完成标准

### 自动门禁

1. 词典类型检查与中英文键完整性测试。
2. 所有公开 Markdown、meta 和演示数据的英文覆盖检查。
3. 中文、英文两次静态构建成功，并生成数量一致的页面集合。
4. 英文 `out/en` 可见文本 CJK 扫描；仅允许逐节点登记的必要专名。
5. 双语站内链接爬取：不得有 404、跨语言误跳或丢失 query/hash。
6. 组件快速入口的精确命中、模糊命中、键盘操作和语言保持测试。
7. 双主题、桌面和移动断点的 a11y/browser gates。
8. 现有生成门禁按顺序运行：`pnpm llms-registry && pnpm conventions`，再执行测试、类型检查、registry 页面 smoke、a11y、size 与双语 www build。

### 本地真实页面验收

至少检查：

- 中英首页与语言切换。
- 中英组件目录、组件搜索和三个组件详情。
- 中英主题页、区块页、整页预览与 changelog。
- 每一套演示至少一个列表页和一个详情/操作页。
- 375px 移动端和桌面端的顶栏、搜索、侧栏与切换器。

### 公开站验收

国内镜像和国外主站分别验证：

- 中文与 `/en` 页面都返回成功并显示正确语言。
- 默认语言规则与显式偏好生效。
- 组件精确搜索可直达同语言详情。
- canonical、hreflang、registry、英文 llms 文件和关键静态资源正确。

只有本地构建、CI、两个部署和上述真实页面检查全部通过，才能宣称目标完成。任一公开站仍旧或部署失败时必须明确报告为未闭环。

## 实施顺序

1. 建立双语构建、语言路由、URL 与 metadata 基础层。
2. 完成共享站点外壳、搜索和组件快速直达。
3. 翻译结构化 meta、组件目录和全部组件 Markdown。
4. 翻译主题、区块、页面、更新日志与生成产物。
5. 按演示域逐组迁移全部页面和数据，并持续运行英文残留扫描。
6. 完成自动门禁、全量构建、浏览器验收与双站发布验证。
